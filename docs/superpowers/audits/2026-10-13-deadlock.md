# 2X Ping: Deadlock server selector audit

Date: 2026-10-13. Repo: C:\Dev\2XPing, branch simple-main-screen (HEAD 3eee989). This was a read-only audit: no repo files or firewall rules were changed.

Evidence used:
- The live SDR config (GetSDRConfig appid 1422450, revision 1791863345) and CS2's (730).
- Deadlock's own install on this PC (D:\SteamLibrary\...\Deadlock, client.dll dated 2026-10-10): its binaries and localization.
- deadlock-api.com's OpenAPI spec and source.
- SteamDatabase's protobuf dumps.
- Valve's SDR and GameNetworkingSockets docs.
- ICMP pings from this PC, which is on STC in Riyadh.

## 0. TL;DR (most important first)

1. **The lock leaks through Dubai. This is the biggest problem.**
   - SDR's ping to a datacenter is "best available relayed route" (Valve: `GetPingToDataCenter`), and the route can enter Valve's network at any relay.
   - Deadlock's own `steamnetworkingsockets.dll` shows how: `Backup router: %s  Ping = %d+%d=%d (front+back=total)`, and the relay ping-reply fields `best_dc_via_relay_pop_id` / `default_dc_via_relay_pop_id`.
   - The app keeps dxb (and the new dfjr) open, and blocks only the relays of the other *hosting* POPs. So every blocked datacenter can still be reached through Dubai.
   - From Riyadh, Valve's own `typical_pings` put the European datacenters about as close via Dubai as direct:

     | DC | via dxb | direct |
     |---|---|---|
     | fra | ~69 | 74 |
     | vie | ~58 | 85 |
     | waw | ~69 | 90 |
     | sto | ~82 | 94 |

     (§3.1 shows how these were computed.)
   - So "lock to SE Asia" (sgp ≈ 106 via dxb) most likely still lets the matchmaker pick Europe.
   - The card then shows "You're playing in one of your regions now ✓" whenever only a relay is seen (CardLogic.cs:55-57). That is a false positive.
2. **The table of hosting datacenters (`Stats.PopToMm`) is wrong in four places.** Sources: deadlock-api's `ServerRegion` enum (taken from the GC's private-lobby region list) and Deadlock's own localization list (`Citadel_ServerRegion_*`).
   - **jnb (Johannesburg) hosts Deadlock** ("South Africa", id 11, in the Europe pool). The app treats it as relay-only, so it is never blocked and is not part of Europe.
   - **bom2 / maa2 (India) and gum (Guam) host nothing.** The app counts them as SE Asia hosts and blocks them, which can lengthen routes for South Asian players.
   - **dfjr (Datapacket Fujairah) is a new POP** that no table knows about. It falls through to relay-only.
   - **hel (Helsinki), fsn (Falkenstein) and eat/mwh (US West) host matches but have no relays** in the config. They can never be blocked, and LoadValve drops them.
3. **Russia is a player pool, not a set of datacenters.** About 18% of live matches (27/150 at the time of the audit) are Russia-pool games. No Valve server region maps to Russia, so they are played on EU datacenters. No POP→Russia mapping exists or should be added. Russia can't be chosen by locking.
4. **Detection names the entry relay, not the match server.**
   - HostRegionOf returns the *first hosting POP among the top-5 hits*, even when a relay-only POP (dxb) carries most of the packets. A backup-router keepalive at ≥20 packets per 15 s is enough to trigger it.
   - The game itself logs the real answer: `Remote host is in data center '%s'`, `Primary router: %s`, `Communicating via relay in '%s'`. These strings are in Deadlock's SDR dll.
5. **Deadlock has no region option left.**
   - `citadel_region_override` (playtest era) is **not in the current client.dll**.
   - Only `citadel_private_lobby_server_region` exists, and it only applies to private lobbies.
   - Matchmaking sends `CMsgRegionPingTimesClient{data_center_codes, ping_times}` and a `region_mode`.
6. **deadlock-api `/v1/sql` is deprecated** ("Direct SQL access will be removed"), with limits of 2 req/min and **20 req/hr per IP**.
   - The Supabase cron calls it about 66 times an hour (supabase-setup.sql:207-221). Most of those calls must be getting HTTP 429.
   - The fix: count `region_mode` from `/v1/matches/active`. That endpoint allows 100 req/s and is CDN-cached for 120 s.

## 1. Research findings (with sources)

### 1.1 How SDR measures ping and picks a route
- Clients ping the relays listed in the network config and build a "ping location". Valve describes the ping estimate between hosts as "a conservative estimate, based on routing through the relay network". `GetPingToDataCenter(popID, *pViaRelayPoP)` returns the "ping time of best available relayed route", and the via-POP is returned explicitly. Sources: [ISteamNetworkingUtils docs](https://partner.steamgames.com/doc/api/ISteamNetworkingUtils), [GNS isteamnetworkingutils.h](https://github.com/ValveSoftware/GameNetworkingSockets/blob/master/include/steam/isteamnetworkingutils.h).
- `GetDirectPingToPOP` is listed separately ("*direct* ping time to the relays at the data center"). So matchmaking data, built from `GetPingToDataCenter`-style values, is **not** only direct pings.
- Deadlock's `game/bin/win64/steamnetworkingsockets.dll` (strings from this install) shows routes have a front relay and a back relay:
  - `Primary router: %s` and `Backup router: %s  Ping = %d+%d=%d (front+back=total)`
  - `Relay %s sent CMsgSteamDatagramRouterPingReply with extra route info about data center %x`
  - Proto fields: `best_dc_via_relay_pop_id`, `default_dc_via_relay_pop_id`, `front_ping_ms`, `interior_score`

  So a relay you *can* reach tells the client its own ping to datacenters whose relays you *can't* reach.
- Game servers in Valve datacenters never expose their IPs. Traffic goes client → relay(s) → server, and the GC issues a `SteamDatagramRelayAuthTicket`. Source: [SDR docs](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay).
- The GC uses client pings to "make good decisions about how to assign players to data centers" (same page).
- Ping data refreshes by itself ("The library will automatically refresh the information as needed"). Deadlock ships its **own** steamnetworkingsockets.dll, so the ping cache lives inside the game process. Restarting **the game** (not Steam) forces a fresh measurement. The app's "restart the game or wait a minute" advice is right.
- Other SDR client options exist in the dll (`SDRClient_ForceRelayCluster`, `SDRClient_FakeClusterPing`, `SDRClient_LimitPingProbesToNearestN`), but I found no Deadlock console path that exposes them.

### 1.2 What the current SDR config looks like (fetched 2026-10-13)
- 37 POPs, 146 relays, IPv4 only, and **no `service_address_ranges` in any POP** (CS2's config has none either).
- Relay port ranges are 27015-27060 for 117 relays, **27015-27140 for 27 relays**, and 27015-27078 for 2. A tool that only blocks 27015-27060 would miss some relays. The app blocks all ports, so it is fine.
- POPs with **no relays**: dlhr, dsto, eat (alias mwh), fsn, hel (alias helm). Aliases also exist: bom→bom2, maa→maa2, tyo1-3→tyo.
- **New POP: dfjr "Datapacket Fujairah (UAE)"**, 1 relay, 2 ms from dxb in typical_pings.
- The Datapacket POPs have [lat, lon] swapped in `geo`. dsto's coordinates are Moscow's.
- `typical_pings` covers only 129 of 666 pairs. dxb has direct entries only to bom2, dfjr, dlhr, hkg, maa2 and sgp, and **dxb–fra is missing**.

### 1.3 Deadlock matchmaking and regions
- Protobufs ([SteamDatabase GameTracking-Deadlock](https://github.com/SteamDatabase/GameTracking-Deadlock/tree/master/Protobufs)):
  - `ECitadelRegionMode` values: ROW=0, Europe=1, SEAsia=2, SAmerica=3, Russia=4, Oceania=5.
  - `CMsgClientToGCStartMatchmaking` carries `CMsgRegionPingTimesClient{repeated fixed32 data_center_codes; repeated uint32 ping_times}` and `region_mode`.
  - Error codes: `k_EResult_NoRegionPings`, `k_eCannotSelectRegion`, `k_eMatchMakingStopped_NoServerRegion`.
- Localization in this install:
  - `Citadel_StartMatchmaking_NoRegionPings`: "Unable to communicate with any Steam Datagram Relay… firewall or the MTU". Players hit this if a lock blocks every relay they can reach.
  - `Citadel_StartMatchmaking_CannotSelectRegion`: "Unable to select a region for matchmaking".
- Region override: guides from the 2024 playtest ([Shacknews](https://www.shacknews.com/article/141164/change-region-deadlock), [esports.gg](https://esports.gg/news/deadlock/how-to-change-server-regions-in-deadlock)) describe `citadel_region_override -1..5`. I grepped client.dll (2026-10-10 build) and it is **absent**. Only `citadel_private_lobby_server_region` remains.
- Which servers actually host Deadlock games. deadlock-api `ServerRegion` (source: `deadlock-api/deadlock-api` `api/src/routes/v1/matches/types.rs`) agrees with the game's `Citadel_ServerRegion_*` strings:

  | ROW | US West 1, US East 2, US North Central 27, US South Central 31, US South East 23, US South West 22 |

  - **None of them is India, Dubai/UAE, Guam or Russia.**
- deadlock-api data:
  - Active matches carry only `region_mode`, never the datacenter. `/v1/matches/active` returned 150 matches by region_mode: Europe 70, Russia 27, ROW 24, SEAsia 18, Oceania 10, SAmerica 1.
  - Per-match `cluster_id` (replay group) exists in `/v1/matches/{id}/salts`. It might map to a server region, but I did not verify that.
- `/v1/sql` is deprecated with 2/min and 20/hr per-IP limits. `/v1/matches/active` and `/v1/info` allow 100 req/s. Source: [deadlock-api OpenAPI](https://api.deadlock-api.com/openapi.json).

### 1.4 How other tools block servers
- [cs2-server-picker](https://github.com/FN-FAL113/cs2-server-picker) blocks relay IPs with Windows Firewall, because the real server IPs are not public. It warns that "Re-routing can also happen anytime, even mid-game", that blocking too much causes match-accept timeouts, and that Deadlock is untested with it.
- Blocking through the hosts file is useless for SDR: relays are contacted by IP from the config, not by DNS name.
- Community reports for CS2 say regions come back after restarting the game, sometimes several restarts ([Steam thread](https://steamcommunity.com/app/730/discussions/0/3952532649330481582)).
- "Failed to reach any official servers" / NoRegionPings means no relay answered ([csdb.gg](https://csdb.gg/how-to-fix-failed-to-reach-any-official-servers-on-cs2/)).

## 2. Audit of the app's Deadlock path

### 2.1 Correctness bugs

**B1. The lock is leaky by design for Middle East and South Asia players.**
- Where: MainForm.cs:2260-2261 builds the block list only from `g.Hosts(r)`; dxb, dfjr and jnb stay open.
- Why: Section 1.1 shows SDR estimates a blocked DC's ping through open relays. From Riyadh, every EU DC stays at 58-87 ms via dxb, while SE Asia is about 106 via dxb.
- Effect: Locking a non-EU region very likely does not stop EU matches. Locking EU only "works" because EU is already the best choice.
- Fix: see I1.

**B2. HostPops is wrong in four places.**
- Where: GameDb.cs:292 builds `HostPops = new HashSet<string>(Stats.PopToMm.Keys)`; the table is Stats.cs:29-37.
- **jnb** is missing. It hosts Deadlock in the Europe pool, so it is never blocked and never part of "Europe".
  - With a lock on, a jnb match is reported as "via relay, hidden" and the card shows ✓.
- **bom/bom2/maa/maa2/gum** are listed as SEAsia hosts, but they are not Deadlock server regions.
  - Locking any non-SEAsia region blocks them. For Indian players they are the entry relays, so routes get longer.
  - Choosing SE Asia "locks" two places that host nothing.
- **dfjr** is unknown to the table, so it is silently relay-only. That is right in effect, but only by accident: any new hosting POP Valve adds will also silently be "relay-only", meaning never blocked.
- **hel** is in the table but never loaded (no relays). That is harmless, but `fsn` and `eat`/`mwh` are absent too. They host matches and can never be blocked.

**B3. HostRegionOf / ShowValveResult name the wrong place.**
- Where: MainForm.cs:1804-1812, 1887, 2108.
- `FirstOrDefault(r => r != null && g.Hosts(r))` over the top-5 hits returns the first hosting POP with ≥20 packets (Stats.cs:290). It does not look at whether a relay-only POP carries 95% of the traffic.
  - SDR keeps a backup router alive alongside the primary (`Backup router: …` in the dll). From Riyadh, the primary is often dxb and the backup often fra or ams.
  - The result is "On: Frankfurt ✓" when the truth is "through Dubai to an unknown DC".
- Even with a direct entry, the entry relay's POP is not the server's POP (front/back routing). A server at hel or fsn can never be named at all.

**B4. The "InMatchRelay" card claims success without evidence.**
- Where: CardLogic.cs:55-57.
- It reads "You're playing in one of your regions now ✓" whenever only a relay was seen. Given B1 and B3, this is the most common case for Gulf players, and it is the one where the lock is most likely leaking.
- The status message at MainForm.cs:1893-1897 says the same: "Your lock still only allows the servers you picked."

**B5. WarnLongerRoute misses or misjudges routes.**
- Where: MainForm.cs:2328-2363.
- `g.Between` (GameDb.cs:60-67) only uses *direct* `typical_pings` entries, which cover 129 of 666 pairs. dxb→fra/ams/vie/waw/sto are all missing, so the open route through dxb is never counted for EU picks.
  - The warning can fire with an overstated gain, or stay silent, depending on which pairs happen to exist.
- It also measures ping with ICMP `Direct.Avg`, uses one hop only, and ignores relay-only POPs that act as the *blocked* path.
- Fix: run all-pairs shortest paths over `typical_pings` (Floyd–Warshall; 37 nodes is trivial). See I3.

**B6. Player stats depend on a deprecated, over-limit endpoint.**
- Where: Stats.cs:120-122 and tools/supabase-setup.sql:207-221.
- The `regions` query runs every minute: 60/hr against a 20/hr per-IP limit, so most requests get 429.
  - `coalesce` keeps old values and `SharedDeadlock` rejects rows older than 10 min, so the numbers flap between shared and per-PC fallback.
  - The per-PC fallback hits the same limit.
- `/v1/sql` will also be removed ("Direct SQL access will be removed").

**B7. LoadValve drops POPs without relays.**
- Where: GameDb.cs:473 (`if (r.Endpoints.Count > 0)`).
- hel, fsn and eat host matches but disappear from the list. The UI can never explain "Helsinki: can't be blocked".
- Smaller points in the same function:
  - The `service_address_ranges` handling (GameDb.cs:471) is dead code against today's config.
  - Only `ipv4` is read (GameDb.cs:466). That is fine today, but if Valve adds `ipv6` relays, the lock will not cover them.

### 2.2 Gaps

- **G1. Russia.** It is in MmRegions (Stats.cs:23) but no POP maps to it, so it never becomes a tile. That is correct. But its ~18% share is counted in the online total (PlayersOf) and shown in the info label without explanation. Explain that Russia is a separate player pool on the same EU datacenters, and that the lock can't choose it.
- **G2. The detected server is not checked against the lock in the normal case.** Most Gulf matches end in the "relay only" branch (MainForm.cs:2142-2150), which reports nothing (no `lock_outside` telemetry). Leaks are invisible in the Issues/telemetry data.
- **G3. Tile pings are direct ICMP** (RegionGroups.Build → BestLatency, MainForm.cs:1047). SDR plays SE Asia from Riyadh at about 106 (via dxb), not 197 as the tile shows. The "best ping" tile can therefore pick the wrong region.
- **G4. Nothing alerts when the SDR config changes** (new POP, new alias, a POP losing its relays). This is how dfjr slipped in.
- **G5. No guard against blocking every reachable relay.** That leads to NoRegionPings or "Unable to communicate with any Steam Datagram Relay". There is also no check that at least one picked POP answered ping before applying the lock.

### 2.3 Wrong assumptions in comments and UI text

| Where | Assumption | Reality |
|---|---|---|
| GameDb.cs:52-55 comment | "The others are only relays… blocking them gains nothing" | Open relays carry routes to *blocked* DCs, so leaving them open is what defeats the lock. Blocking them gains strictness and costs ping. |
| RegionGroups.cs:258-259 | "Relay-only locations (Dubai, Johannesburg)" | Johannesburg hosts matches (Europe pool). |
| Stats.cs:28 | PopToMm is "the clear ones" | Contains three non-hosts (bom2, maa2, gum); missing jnb, fsn, eat. |
| MainForm.cs:1801-1803 | The DC the game is on comes "from the addresses it talks to" | Those addresses are front/back relays; the server DC can differ. |
| LockServers toast "You'll only be matched on: …" | Firewall makes other DCs unreachable | It only makes their *direct* entry unreachable. |

## 3. Concrete improvements (priority order)

**I1. Strict, route-aware lock (fixes B1 and B4).** Compute the open set from data instead of "all relay-only POPs":
1. Build `dist[a,b]` = all-pairs shortest path over `typical_pings` (GameDb.LoadValve already parses them; add Floyd–Warshall there). Let `ping[o]` be the measured ping to each POP's relays.
2. Picked target: `P = min over picked p, open o of ping[o] + dist[o,p]`.
3. For each relay-only POP `o` (dxb, dfjr, bom2, …): if some *blocked* hosting DC `b` has `ping[o] + dist[o,b] <= P + margin` (margin about 15-20 ms), then `o` must be blocked as well. If blocking it raises P a lot, tell the user the trade-off, for example: "SE Asia without Europe: 197 ms (direct). Dubai has to be closed because it reaches Europe in ~60 ms."
4. Never block every POP the player can reach (G5). Keep at least one picked POP that answers.
- For the owner's line, this means:
  - Europe: no change (keep dxb).
  - SE Asia: block dxb and dfjr too, and warn that the ping becomes ~197 ms.

**I2. Fix the hosting table (B2, G4).** In Stats.cs:29-37:
- Add `{"jnb","Europe"}`.
- Remove `bom`, `bom2`, `maa`, `maa2`, `gum` (they become relay-only).
- Keep `dfra`/`dvie`. They are probably in the EU-West (3) / EU-East (9) clusters; unconfirmed, but blocking them outside an EU lock is right either way.
- Add the no-relay hosts `fsn`, `hel` and `eat`/`mwh` as known hosts that "can't be blocked".
- Better: generate this table from deadlock-api's `ServerRegion` enum (a ServerRegion-id → POP mapping kept in the repo) and log telemetry when GetSDRConfig contains a POP missing from the table.

**I3. WarnLongerRoute on real routes (B5).**
- Replace `g.Between` with the shortest-path `dist`.
- Compare *with the lock* (ping through the open set) against *without the lock* (ping through every POP) for each picked DC.
- Report the extra ms and the alternative ("tick X" or "allow Dubai").

**I4. Honest detection (B3, B4, G2).**
- Only treat a hit as primary if it has ≥50% of the game's packets. Report "Entering at: Dubai (Valve relay)" rather than "On: Frankfurt".
- Change the InMatchRelay card to neutral wording ("Through Valve's relay in Dubai; the match server can't be seen from here"), with no ✓, and add a "check in game" hint (see §4 step 3).
- Optionally, if the user starts Deadlock with `-condebug`, read `game\citadel\console.log` for `Remote host is in data center '…'`. That is authoritative, and it lets the app send `lock_outside` correctly.

**I5. Tile ping = SDR route ping (G3).** Use `min over open o of ping[o] + dist[o,dc]`, showing "via Dubai" when that path wins.
- For Riyadh, SE Asia would show ~106 ms (via dxb), not 197.

**I6. Stats source (B6).**
- In Supabase and Stats.DeadlockActivity, fetch `/v1/matches/active` and count `region_mode` (0 Row, 1 Europe, 2 SEAsia, 3 SAmerica, 4 Russia, 5 Oceania) with `start_time > now-3600`. It is the same "top 200 watch tab" sample the SQL query reads.
- Keep `/v1/info` every 10 min.
- Drop the hourly `player_match_history` SQL, or move it to the data lake (data.deadlock-api.com).

**I7. Russia (G1).** Add a footnote in the region list, for example: "Russia: ~N players, separate queue on EU servers, can't be chosen by locking".

**I8. Small fixes.**
- LoadValve: also add `ipv6` relays (and block them).
- Keep the no-relay hosting POPs as display-only rows.
- Keep blocking all ports and protocols: 27 relays use ports up to 27140.

## 4. Verification procedure for the owner (Riyadh, STC)

Do these in normal (unranked) matches.

1. **Setup.**
   - In Steam → Deadlock → Properties → Launch options, add `-condebug`. The console is then also written to `D:\SteamLibrary\steamapps\common\Deadlock\game\citadel\console.log`.
   - The console key is F7. If it is disabled, add `-console`.
   - In 2X Ping, unlock, then run `netsh advfirewall firewall show rule name="2XPing-RegionLock"`. It should report no rules.
2. **Baseline, unlocked.**
   - Start Deadlock and wait about 30 s in the menu.
   - In console.log, find the line `Ping location: …`. Note the values for dxb, fra, vie, waw and sgp, and any "via" markers.
   - Queue a match. Once in, search console.log for:
     - `Remote host is in data center` (the real server DC)
     - `Primary router` and `Backup router … (front+back=total)` (which relays carry the traffic)
     - `Communicating via relay in`
   - Press "Which server am I on?" in 2X Ping and write down what it says.
   - Expected: server in an EU DC, primary router most likely dxb. If the app says "Frankfurt" but the console says data center X via dxb, that confirms B3.
3. **Leak test.**
   - Lock **SE Asia** in 2X Ping. Fully close and reopen Deadlock (not Steam).
   - Read the new `Ping location:` line. If fra, vie and waw still have values (they will be reached via dxb), the lock is leaking (B1).
   - Queue 2-3 matches and record `Remote host is in data center` each time. Any EU DC confirms B1.
   - The app's card meanwhile shows "You're playing in one of your regions now ✓", which confirms B4.
4. **Strict test, manual, your own decision.**
   - With the SE Asia lock still on, in an admin terminal: `netsh advfirewall firewall add rule name="2XPing-Test-Dubai" dir=out action=block remoteip=185.25.183.163,185.25.183.179,89.222.117.194` (the dxb and dfjr relays, from the current SDR config).
   - Restart Deadlock and check `Ping location:` again. EU should now be gone or much higher, and SE Asia about 197 ms.
   - Queue and record the data center. Expect sgp or hkg, with a longer queue.
   - Remove the rule afterwards: `netsh advfirewall firewall delete rule name="2XPing-Test-Dubai"`.
5. **Europe lock.**
   - Lock Europe, restart the game, play 2 matches.
   - The data center should always be an EU one (ams, fra, lhr, par, mad, vie, waw, sto, hel, fsn). If you ever see jnb, that confirms B2.
6. **Ping check.** Compare the in-game ping (scoreboard or net display) with the app's tile for the region. A large gap (for example SE Asia: tile 197, game ~106) confirms G3.
7. **Clean up.**
   - Unlock and run the `netsh … show rule` check again.
   - Remove `-condebug` if you want; the log grows by roughly MBs per session.

Send the `Remote host is in data center`, `Primary router` and `Ping location` lines from steps 2-5. Those few lines are enough to confirm or reject B1-B4 and set the margin in I1.
